# Expo Planner

A browser app for planning crew for exhibition build-up (montering) and tear-down (demontering). It replaces the planner's Excel workbook (`Bemanning_Behov_24 måneder.xlsx`), which it does not read: the app stands on the source exports alone. The workbook was the model for the rules and the test data while the app was built.

Open work is listed in [docs/TODO.md](docs/TODO.md), what each page does in [docs/features/](docs/features/README.md), and what was built and decided part by part in [docs/decisions.md](docs/decisions.md). How the old workbook works is described in [docs/kalender-workbook.md](docs/kalender-workbook.md). `design_docs/` holds the designs the planner made for parts of the app: the rules of the Kalender's look (`kalender-v9`, normative), Bemanning (`bemanning`, `bemanning-v2`) and Innleid (`innleid`). The notes of an abandoned earlier attempt are deleted (2026-10-19).

## Commands

```bash
npm run dev     # dev server
npm test        # Vitest, all tests
npm run build   # type check (tsc -b) + production build
npm run lint    # oxlint
```

Run `npx tsc -b` after edits; tests are type-checked through `tsconfig.test.json`, not by Vitest. A `.test.ts` runs without a DOM, a `.test.tsx` in jsdom (`vite.config.ts`); a `.ts` test that needs a DOM says `// @vitest-environment jsdom` in its first line. Fixtures read by tests only are in `src/test/`. The component tests of the Kalender and Bemanning (`kalender/Kalender.test.tsx`, `bemanning/Bemanning.test.tsx`) drive the page through the real store on a fake IndexedDB, with a small invented workspace (`ui/test/kalenderHarness.tsx`); they are what says a split or a cleanup changed no behaviour.

## What the app does

Six tabs, all in Norwegian: Kalender and Behov, where the planning is done, Resultat, which compares it with the budget, and the planner's tables in three: Haller (VenYou, Prosjekter, Hallregler), Mannskap (Personell, Leverandører, Kompetanser) and Oppsett (Produkttyper, Tekstregler, Utelatte artikler). What each page does, in detail, is in [docs/features/](docs/features/README.md): read the file of the part you are changing before you change it.

- **Kalender** has two modes. **Plan** ([plan.md](docs/features/plan.md)) is FTE per day on planning rows in a hierarchy the planner groups, under the date header, the hall calendar and the staffing lines. **Bemanning** has two parts: the permanent staff by name against the hours left per competence ([bemanning.md](docs/features/bemanning.md)), and **Innleid**, the hours after them ordered from suppliers ([innleid.md](docs/features/innleid.md)). **Arbeidsplan** prints a day plan and a week plan from Bemanning ([arbeidsplan.md](docs/features/arbeidsplan.md)).
- **Behov** ([behov.md](docs/features/behov.md)) is the demand: the Visma lines reviewed, and the planner's own lines.
- **Resultat** ([resultat.md](docs/features/resultat.md)) is the season against the budget, per project.
- **Haller**, **Mannskap** and **Oppsett** ([haller.md](docs/features/haller.md), [mannskap.md](docs/features/mannskap.md), [oppsett.md](docs/features/oppsett.md)) are the planner's own tables, each with «Eksporter» and «Importer fra fil» behind «Fil».

Sources read from files: the Venyou export, Visma exports, and optionally `Prosjekt.xlsx` and `Kpier.xlsx` as one-time shortcuts; see [docs/features/README.md](docs/features/README.md).

### Rules of the code that the feature notes carry

- The width of a day is the style variable `--col-w`; lay out by it (`daysWide` in `kalender/layout.ts`), never by a width in pixels from `colW`, or the zoom has to draw every line again on each frame.
- What a component of Innleid shows is worked out in `domain/hire.ts` and tested there; the components only draw it. The same holds for the rules of Bemanning (`domain/staffing/`) and of the plan (`domain/spread.ts`, `kalender/strokes.ts`).
- The lines of the Kalender's grid get the selection as plain values per line and their handlers through `useStableActions` (see below), so a scroll frame draws no line again.

## How it fits together

- `src/domain/` – pure logic, no React and no storage. Start here.
  - `types.ts` – the `Workspace` and its records.
  - `numbers.ts`, `collections.ts` – small helpers every part shares: a typed decimal, `clamp`, and `pushTo`, which groups into a map of lists (write no `map.set(k, [...(map.get(k) ?? []), v])`, which copies the list on every add).
  - `visma.ts` – Visma booking lines → demand lines. One line per project × Avdeling × work type × hall; hours = quantity ÷ rate × (1 − Effekt). Units `ordre` and `stands` count stands; other units sum `Totalt antall`.
  - `kpi.ts` – the KPI table: product types with their unit in use, competence and rates, what each lacks, and merge/replace for imports.
  - `venue.ts`, `venueImport.ts` – the hall calendar, merging a Venyou export, hidden bookings.
  - `projects.ts` – the project table: a row per name a project goes by (`ProjectRef`: name, number, and a year only where the number does not begin with it). Matching an event to a project by name and year, the suggested numbers, the edits of the table, what follows a number (`projectFollowers`), and the rows of the Prosjekter tab (`projectRows`).
  - `locations.ts` – places a demand line in a hall of the hall ledger, for its project, and says what placed it (`placeOf`, shown as «Regel» on Behov): the planner's choice for that Hall/Sted text in the project, else the choice for the text in every project, else the hall or place the whole text names, however it is spelled («Studio 3» is STUDIO3; `spelled`), else the first of the planner's word rules whose words it holds, else «Mangler hall». Places that stand for several halls («B» for B1 to B4, with their days together in the Kalender) and the word rules («a text that holds scene counts under C») and the choices for texts are the planner's own, one record (`HallRules`, stored as `hallRules`: `places`, `phrases`, `choices`). What is stored is all there is: nothing is added while a text is read, and nothing about which halls belong together is in the code. A place collects its halls unless the planner unticks it (`collectedIn`): what lands in «B1» counts under «B», and the halls of such a place are no places of their own. The first time halls are read in from Venyou, examples are written into the rules (`exampleRules`, in `importVenue`): the letters several numbered halls share as places, and a letter with one numbered hall as a choice («A» is «A1», which places «Hall A»), to change or delete. They are never added again. The code itself reads only names: the whole text is the name of a hall or a place. «Ufordelt» (`PROJECT_HALLS`) is the place of demand that is not shared out on halls, ordered as one sum for several, as «Hall C, D, E»; it has the days of all the project's halls. It holds that demand alone, where a planning row for «Alle haller» covers the demand of every place. It is given by the planner or a rule, never fallen to. A text left as «Mangler hall» is offered a place (`suggestHall`), in the Plassering cell and for all at once: the one place it names somewhere in it, in one word or several («cafe hall D», «Kafé ved Studio 3»), «Ufordelt» where it names several, or the only hall of its project where it names none, which is a choice for that project alone. The line keeps its own text.
  - `hallReview.ts` – the demand as the rules place it (`reviewPlacing`): the lines per step of the order, what each choice and each rule for words is used for, and the texts that are left, with their offers. Hallregler and the notice on Behov count from it.
  - `areas.ts` – the halls gathered in the planner's areas (`HallRules.areas`), as a tree, what the planner has unticked of it in the Kalender, and the projects that are out of sight with it. An area decides what is shown, never where demand counts; that is the places of `locations.ts`.
  - `plannedRows.ts` – demand under «Planlagt» shows as suggested Kalender rows, one per project × phase × hall × competence × Avd. A row with no hall or Avd. covers all of them.
  - `calc.ts` – required hours per row (like the workbook's TIMER column), daily need, capacity.
  - `calendarRange.ts` – the Kalender's period follows the hall bookings.
  - `hire.ts` – the rules of Innleid (`design_docs/innleid/RULES.md`): an order is people from a supplier for a competence, a day and a time, waiting or confirmed; how far the orders cover the hours that remain of a competence on a day after the permanent staff (`coverage`), a day's Avvik over its competences (`deviation`), the count an order is filled in with (`planOrders`), answers and counts, and the order as text. Hours, never FTE, but for the Kalender: the confirmed orders are its staffing line «Innleid (FTE)», added to «Tilgjengelig» (`hiredLine`); orders that wait count nowhere. A shift is paid its length less a lunch as long as the normal day's from six hours (`hireHours`), and «Dag» is the normal day of Innstillinger (`shiftTimes`). `suppliers.ts` – the suppliers and what a file of them changes; what a file of names with a column per competence shares with the people's is in `competences.ts` (`oneEach`, `competencesFromFile`, `withFileCompetences`).
  - `result.ts` – Resultat: the season's rows and sums, a project's hours per competence and phase, and the budgets with what a file of them changes.
  - `staffing/` – the rules of Bemanning, in five modules, each importing only those before it: `intervals.ts` (time within a day, paid hours with the lunch left out, overtime), `time.ts` (when a person can work, which blocks count, absence, overtime per day and week, and the staffing lines of absence and overtime), `edit.ts` (painting and editing assignments: the brush, the eraser, moves, copy and paste), `balance.ts` (the balance of demand and assigned hours per competence and day, free capacity, unresolved blocks) and `projectBalance.ts` (that balance per project and place, a stroke cut to where the demand is met, and hours carried to the next day). Their tests are beside them, `staffing.test.ts` with the checks D1–D23 of the design's ACCEPTANCE.md. A block, an order of Innleid and hours moved to the next day can be for a project (`projectNo`, the Claude Doc «Prosjektmerking: byggeplan», 2026-10-21); `buildProjectBalance` shares that balance out on the projects over the whole workspace: tagged hours first, then the untagged by what each project lacks, the demand without a number as a recipient of its own (`NO_PROJECT`) and what none lacks as «Ikke fordelt». It counts the permanent staff alone for Bemanning, and the confirmed orders too for Resultat. Each project's part is shared on its places one step further (`places`, `PROJECT_PLACE` for a row of all its halls or «Ufordelt»): a block painted on a place's line has the place (`Assignment.hall`, only with a project), and the project's other hours go to its places by what each lacks. `workPlace.ts` says where a block's hours are from that (`blockPlaces`), and which places a project has booked on a day (`bookedPlaces`), for the work plans. Nothing of it is stored, and no edit joins work of two projects or two places. `competences.ts` – the list of competences and their styles, and edits to people.
- `src/import/` – file readers and writers. `xlsx.ts` is a small own reader (cached values only) and writer (`writeXlsx`: plain values under a heading); a table the app exports is written with it and read back through `firstSheetWith`, `column` (a heading under any of its spellings) and `cell`, with `FileFormatError` where the file lacks the headings, as `kpiFile.ts`, `personellFile.ts`, `leverandorerFile.ts`, `kompetanserFile.ts`, `prosjekterFile.ts`, `budsjettFile.ts` and `hallreglerFile.ts` (a sheet per list) do. What a file changes is worked out in the domain (`mergeKpi`, `mergePersons`, `mergeSuppliers`, `mergeCompetenceStyles`, `mergeProjectList`, `mergeBudgets`, `mergeHallRules` and their `diff…`), not in the reader; the counting of a diff is `diffBy` in `domain/tableDiff.ts`.
- `src/store/` – `records.ts` (the workspace as records of the shape the sync will have: a record per thing a planner edits, a planning row's days as records of their own, the Visma lines worked out and never stored; `diffWorkspace`, `applyDeltas`), `db.ts` (Dexie/IndexedDB: the records in one table), `workspaceStore.tsx` (all mutations: each hands `commit` the next workspace, whose changed records become the undo step and are written in one transaction per event), `backup.ts`, `prefs.ts` (view preferences per browser, in localStorage).
- `src/sync/` – the shared copy (`docs/supabase-sync-plan.md`): the schema is `supabase/schema.sql`, with `002_members.sql` and `003_owner_and_channel.sql` (the owner alone manages members; the Realtime channel is private) run after it by hand; `engine.ts` sends the outbox and reads what is new, in whole batches; `client.ts` is Supabase, configured by `VITE_SUPABASE_URL` and `VITE_SUPABASE_KEY` (without them the app is local only); `CloudProvider.tsx` holds the sign-in and switches the browser database between this browser's own (`expo-planner`) and the shared workspace's (`expo-planner-<id>`), whose writes also go to an outbox in the same transaction (`db.ts`).
- `src/ui/` – one folder per tab, and `bemanning/` for the Kalender's Bemanning mode. `kalender/Kalender.tsx` is a custom virtualized grid, put together from hooks: `usePlanRows` (the rows, their lanes and windows), `usePlanGrid` with `usePlanCells` and `usePlanStrokes` (the selection, the keys, typing, copy and paste, and the tools drawn across the days), `useModes` (the modes and parts with the zoom between them), `useStaffingLines` and `useDayHover`, and `PlanRows.tsx` draws the rows of the plan; `kalender/rows.ts` builds the row hierarchy from the chosen grouping, `kalender/strokes.ts` works out what the pencil, «Foreslå plan», a pull of a span's end and a paste would write, and `kalender/GridRows.tsx` holds the lines of the grid as memoized components. They get the selection as plain values per line (`CellEdit`) and their handlers through `useStableActions`; keep it that way, or every line is drawn again on each scroll frame. What the tabs share is in `dom.ts` (among it `count`, a number with what it counts in the singular or the plural: write no other), `format.ts` (figures, hours and times of day; the names of days and months and the texts of dates are `weekdayName`, `monthShort`, `dayText`, `periodText` and the like in `domain/dates.ts`), `toolKeys.ts` (V, B and T for the tools of every mode), `cssVars.ts` (the sizes and times the style sheets share with the code, set on the page as variables: write a number in one place), `personell/CompetenceChips.tsx` (the competences someone has, as chips in a cell of Faste and of Innleid), `RegisterHead.tsx` (the band of sand of a tab of tables, with its pages and their counts), `BandFigures.tsx` (a page's key figures as the lower half of its band, on Resultat and Behov), `RowOrder.tsx` (rows of a table put in order by a grip or arrows, as on Kompetanser and the word rules of Hallregler) and `common.tsx` (undo buttons, message banner, merge-or-replace dialog, `FormDialog`, the frame of a dialog that adds something new, and `SidePanel` with `PanelToggle`: the frame of a panel that slides in over a page, which row details and the Person panel are written in), `files.ts`, `fields.tsx` and the table of the ledgers: `DataTable.tsx` draws it from a list of columns (`Column` in `useTable.ts`), each saying what its cell shows and what it is filtered and sorted by; `useTable.ts` holds the filters and the sorting, `ColumnHead.tsx` is the heading, and the rules are in `columnFilter.ts` and `columnSort.ts`. A new table of rows is a `DataTable`, not a `<table>` of its own; the summary on Behov is not a flat list and is written out. The tabs of tables (Haller, Mannskap, Oppsett) draw their rows on a grid of their own (`.op-table` in `register.css`), grouped, with a search and a filter switch; where one needs column filters, as Uplassert on Hallregler, it takes them from `useTable` with `ColumnHead as="span"`.
- `src/styles/` – the style sheets, imported in this order by `main.tsx`: `tokens.css` (fonts, colours and text sizes, light and dark), `base.css` (controls, the shell, menus, dialogs), `tables.css` (the ledgers of the other tabs), `behov.css`, `register.css` (the tabs of the planner's tables), `resultat.css`, `kalender.css`, `inspector.css` and `bemanning.css`. Each rule is written once; do not add a later rule that overrides an earlier one, change the rule. A colour is a token of `tokens.css`; a `color-mix()` stays in the rule where it is used once, or where it mixes a colour set per element (`--cc`, `--heat-c`, `--phase`), which a token on `:root` cannot know. A mix used in several places for the same thing is a token, made again beside every place the colours it mixes are given another value (as `--attention-ring` with `--alert-warn`).
  The look of the Kalender follows `design_docs/kalender-v9/DESIGN-RULES.md`, which is normative: read it before changing a line, a fill or a weekend in the grid. In short: a rule is there to be read along, so only the date header and the lines that are typed in (rows, a folded level, the people) have rules between the days; a line of figures that is read across has a rule under it and none between the days (the staffing lines of Plan, and a competence's line in Bemanning when it is not compact), which is the planner's own addition to the rules; a level has one line above it, over the days alone where it is not a top level, so the label column has lines above top levels only, and the strong line means a top level and nothing else; sections are set apart by a heading on a neutral tint, which is not a line of days: no weekends, no red days and no today line go through it (the planner's choice, where the rules have the weekends go on through); the planned days of a row are a span in the colour of its work phase, a bar behind the figures that is rounded where a run of days with FTE starts and ends, and the cell has no fill of its own (`run-start` and `run-end` in `AllocRow`); a folded level, which takes FTE, shows its sums as spans the same way, in the colour of the phase most of the day's FTE is for (`spanClass`), and an open level shows none; a weekend is one step darker than its line and never see-through; a line (`.grid-row`) is never given a see-through border. The names differ from the mockup's: the four lines are `--grid-col`, `--grid-row`, `--grid-phase` and `--grid-top`, the weekends `--weekend` and `--band-we`, the tint of a section `--section`. The colour of the mode is in the band alone, the page header and the planning bar (`.mode-band`, the `--mode-*` tokens, set by `data-mode` on `.kalender`): olive for Plan, spruce green («Gran») for Bemanning and fjord blue for its part Innleid (`data-part`), never the accent; the two lines that frame the band are darker than its fill in both palettes. An alert on the band is a solid chip with its own ink (`--alert-warn`, `--alert-block`, text `--alert-on`): never a tinted fill and never the ink of the band. Today is one line per pinned block (`.today-line`), not a mark per cell; it is seen wherever a day has content and breaks at the heading of a section, which lies over it (the planner's choice, where the rules have it unbroken).

Everything is stored in the browser (IndexedDB database `expo-planner`). Signed in, a shared workspace is kept in a database of its own in the browser and synced with Supabase (`src/sync/`); there is no server of our own.

## Conventions

- UI text is Norwegian (bokmål). Code, comments, commit messages and docs are English.
- The venue system is called **Venyou** (venue + you). "Venyoo" in `design_docs/` is a misspelling.
- Keep source and status apart: a Visma line always stays a Visma line; the planner toggles it in or out of the plan. Decisions the planner makes (Effekt, in plan, chosen work type, chosen location, hidden halls, the names of a project) are stored separately from imported data, keyed so they survive the next import.
- Visma is today's source of commercially ordered demand, not a part of the model. What the plan rests on is the chain from a quantity of a product type, through its KPI rate, to hours, and the product type's name is the key that joins an ordered line to its rate. Keep what is Visma's own (column names, the number and brackets around a type, that a stand number begins with the letter of its hall, the layout of the file) in the reader (`import/vismaExport.ts`: `vismaProductType`, `vismaHall`). The domain is handed a product type's name and a Hall/Sted text and knows nothing of how Visma writes them. The KPI table, the files the app writes and the planner's decisions are keyed by the product type's name (`productTypeKey` in `domain/kpi.ts`), so they hold when the orders come from another system.
- Reference data lives in editable tables in the app. A file import is at most an optional shortcut and must offer merge or replace when the table already has content.
- The planner tests from a clean state, so there are no migrations for data stored by earlier versions: when a stored shape changes, change it, and do not add code that reads the old one.
- Every mutation goes through `workspaceStore.tsx`, is undoable, and is persisted. Edits made in one user action form one undo step. A mutation works out the next workspace and hands it to `commit`; what to store and undo follows from the records that differ (`records.ts`), so there is no write code per table.
- New domain logic gets a test next to it.

## Data and privacy

All `.xlsx` files and `example_data/` are git-ignored: real exports contain customer and booking data. Never commit them, and do not copy customer names from them into tests, docs or commit messages. Event and project names already used in tests (VVS, Hage, Oslo Motor Show) are fine.

Testing is done on invented data only (2026-10-19): the app has been checked against the real files, which the planner keeps outside the project, and the tests against them are deleted. Claude does not open or read real exports. The invented season is made by `src/demo/demoData.ts` (23 events in 12 halls over September 2026 to June 2027, Venyou and Visma exports in their layouts, and the KPI, Kompetanser, Personell (20 people), Leverandører (10, most offering one or two competences) and budget tables as the app exports them; no customer, order number or contact person) and checked by its test. `npm run demo-data` writes the files to `demo_data/` (git-ignored) to read into the app. A browser profile that has held real data must be emptied («Slett alt og start på nytt») before Claude looks at it.

## Trying the app with test data

The readers of the Venyou, Visma and KPI files are checked against the invented files in `src/demo/demoData.test.ts`; a change in the real layouts shows when the planner reads in a new export. To try the app in a browser without file dialogs, start the dev server and load a file from `demo_data/` through Vite's `/@fs/` path into the hidden file input (see the test notes in docs/TODO.md).

## Working with the user

- Work on a branch, push it, and report. The user says "merge to main"; then fast-forward main, run the tests, push, and delete the branch locally and on GitHub.
- The user tests in a clean state: Innstillinger → "Slett alt og start på nytt", then reads the sources in one by one.
- Staffing lines: the absence from Bemanning is in the Kalender (2026-10-07). Lines typed in by hand (Innleid, trade crews, Admin) came with the workbook only and are removed with it (2026-10-08); the Kalender's staffing lines are «Faste» and those worked out from Bemanning: absence, overtime and, since 2026-10-13, the confirmed orders of Innleid. Innleid is his design for hired crew (`design_docs/innleid/`), built a slice at a time on his word. Trade crews and Admin are not part of it: do not start on them until he asks.
